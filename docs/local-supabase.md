# Local Supabase

`scripts/local-supabase.py` is a script that starts and checks a local Supabase. It requires Docker Desktop for macOS,
the Docker CLI, the Supabase CLI and Python 3 (tested with Supabase CLI 2.90.0).

```sh
python3 scripts/local-supabase.py
```

If Docker Desktop is stopped, it starts it and waits up to 120 seconds.
It uses the Unix socket of the local-only `desktop-linux` context,
and never uses the caller's `DOCKER_HOST` or another context.
`supabase start` reuses existing containers and volumes.
The first run takes time because it pulls the images. The overall internal deadline is 540 seconds.
Even after a timeout no data is deleted, and the script can be run again.

To avoid conflicts with other projects, it uses ports API 55321 / DB 55322 / mail 55324 (Mailpit's HTTP API; SMTP is 55326 — where the team-docs sample sends notification mail in the mail-sending integration test).

The configuration is the managed `supabase/config.toml` generated by `supabase init --yes`.
The script does not run init and does not change the working tree.
The generated `.temp` / `.branches` are excluded by Supabase's `.gitignore`.
A missing configuration, missing dependencies, a startup failure or a connectivity failure ends with exit 75.
Because the CLI output contains connection information and keys, the raw output is never logged, on success or failure.
On failure, check the displayed command in a local terminal.

The checks are PostgreSQL's `SELECT 1` and HTTP 200 from Auth's health endpoint and JWKS.
It does not create app tables, seed, reset or delete data.
Automatic seeding and the unneeded Studio/Realtime/Edge/Analytics are disabled.
The API's exposed schemas are empty; Auth, mail capture and Storage (for the attachment integration test) are enabled.
This does not prove that the production authentication configuration is correct.

## Passing connection information to check commands

An export from the script does not propagate to the caller's shell.
With the following form, the connection information obtained at run time is passed only to the child process's environment.

```sh
python3 scripts/local-supabase.py --exec python3 scripts/run-sample-frontend-backend.py --oauth
```

`--exec` does not start anything; it reads the local status and runs the given command.
`sample` itself also requires `NYXIS_SUPABASE_ISSUER`, so when starting it directly with `--exec`, the caller provides it
(the startup script above prepares the isolated DB, the JWKS relay and the issuer together).
It passes `NYXIS_DATABASE_URL`, `NYXIS_SUPABASE_URL`, and, when available,
`NYXIS_SUPABASE_ANON_KEY` / `NYXIS_SUPABASE_SERVICE_ROLE_KEY`.
It never saves connection strings or keys to files and never uses shell eval.
Only a DB URL for localhost port 55322 and the postgres DB is accepted.
Check commands themselves must not log environment variables either.
This URL is a postgres connection for local checks, not a production dedicated-role configuration.

When running inside a sandbox, permission for the Docker socket and for connections to localhost is needed separately.
This script does not change the sandbox configuration.

## Regression check of the script

```sh
python3 scripts/check-local-supabase.py
```

On a real machine, run the script twice and confirm that both exit 0 and that
`git status --porcelain` is identical before and after. Stop it manually with
`supabase stop` only when needed, and do not use `--no-backup` or `db reset`.

## Anonymous HTTP check against a real DB

```sh
lake build
lake build --dir examples/bulletin-board/backend
python3 scripts/local-supabase.py --exec python3 scripts/check-local-postgres-http.py
```

It creates a local-only DB with a unique name, builds the tables with `initSampleDatabase`, and
inserts test rows. Over `sample`'s real HTTP path it checks reading public posts, rejection of drafts and
writes, unchanged DB rows after a rejection, and that an update from a separate SQL connection is reflected in the next HTTP request.
On exit it stops the child server and deletes only the DB newly created by this run.
It does not change existing app DBs or Auth data. It does not display passwords or connection information.
The check port is 18116 (changeable with `NYXIS_LOCAL_HTTP_PORT`), and the JWKS fetch check (`check-sample-jwks.py`) uses 18117
(`NYXIS_SAMPLE_JWKS_PORT`).

This checks only the anonymous path; the 3 sections below cover authenticated principals.

## Test ES256 JWTs and a 4-principal check against a real DB (dependency adoption check)

```sh
lake build
lake build --dir examples/bulletin-board/backend
python3 scripts/local-supabase.py --exec sh scripts/check-jwt-dependency.sh --local-postgres
```

In addition to the existing JWT dependency check, it uses a dedicated DB with a unique name and a test-only server, and checks over HTTP
reading, editing, deleting and publishing/unpublishing public posts and drafts, creating, and granting/revoking admin rights,
as anonymous, the author, a third party and an admin. After each operation, it compares all User/Post rows from an independent SQL connection,
confirming no change on rejection and the effect on permission. It also checks that granting and revoking rights is reflected in the next HTTP request, and
that reading and editing drafts is rejected with JWTs that have a bad signature, are expired or have a wrong issuer.
It uses the same local URL, Docker and port checks and dedicated-DB cleanup as the existing anonymous check.

The keys and JWTs are test values made with OpenSSL / the approved Lean bindings in a temporary area,
not JWTs issued by Supabase Auth. The test server's fixed clock and JWKS never connect to
production. This is a check of the dependencies and the core verifier; the evidence for the main path is "Integration check of the sample itself with Auth-issued JWTs" below.

## A 4-principal check against a real DB with Supabase Auth-issued JWTs

```sh
lake build
lake build --dir examples/bulletin-board/backend
python3 scripts/local-supabase.py --exec sh scripts/check-jwt-dependency.sh --local-auth
```

After also running the earlier JWT and real DB checks, it creates 3 test users with unique mail addresses in local Auth.
It passes the hash of a magic link generated with the admin API to `/verify` and obtains Auth-issued JWTs without
using passwords. This obtains test sessions following [Supabase's magic link API](https://supabase.com/docs/reference/javascript/auth-admin-generatelink).
It also confirms each JWT's principal with Auth's `/user`.

It fetches the public JWKS and leaves verification to the approved OpenSSL verifier: ES256 only, the correct issuer, the authenticated audience and
the real clock. It uses the real user IDs in test rows of the dedicated DB, and with HTTP for 4 principals and comparisons of all rows confirms
permission, rejection and persistence, and that changes of rights are reflected in the next request.
The admin attribute is decided by rows in the app DB, and Auth's service_role credential is never sent to the app over HTTP.

Only `http://127.0.0.1:55321` is accepted as the Auth URL. On exit it deletes only the users and DB newly created by this
run, and also confirms that a GET of a deleted user is 404.
JWTs, OTP hashes, keys and connection information are never saved to files or logged; only a public JWKS file is created temporarily.

This check uses a test-only server. The check of the main path is the next section.

## Integration check of the sample itself with Auth-issued JWTs

```sh
lake build
lake build --dir examples/bulletin-board/backend
python3 scripts/local-supabase.py --exec python3 scripts/check-sample-jwt-db.py --local-auth
python3 scripts/local-supabase.py --exec python3 scripts/check-sample-jwt-db.py
```

The first command verifies Auth-issued magic link JWTs with the real sample.
It compares HTTP and persisted rows for anonymous, the author, a third party and an admin.
Local Auth's `auth.jwt_issuer` is `https://localhost:55325/auth/v1`.
It uses the setting in [the configuration definition of CLI 2.90.0](https://github.com/supabase/cli/blob/v2.90.0/pkg/config/auth.go).
If you change this setting while local Supabase is already running, it takes effect after `supabase stop` and
a restart with `python3 scripts/local-supabase.py`. No data reset is needed.

Only during the check, a temporary TLS server runs on port 55325 and relays the fixed local Auth public JWKS, fetched on every request.
The sample's HTTPS, certificate, host, issuer and signature verification are kept.
The test CA is passed only to the child process's environment, and no test configuration is exposed to the app or over HTTP.
Auth's admin credentials and JWTs are never sent to the JWKS fetch destination.
On exit it deletes only the 3 users and the dedicated DB it created, and saves no JWTs, OTPs or credentials.

The second check, without arguments, checks HTTP and persisted rows with the approved ES256 fixture,
confirming success with a valid JWT and anonymization / rejection of draft reads and edits with a bad signature, an expired token or another issuer.
In both modes, with the same sample process, it checks 4 kinds of JWKS failure and recovery, 8 DB failures with rollback/recovery,
and 101 authenticated reads exceeding the connection limit of 100 with 0 connections left over while the server is alive.
These 2 checks are the checks of the sample's own path. They do not substitute for cloud configuration or TLS verification on Linux.

## Check of the fetch range of decision materials (100,000-row scale)

```sh
lake build
lake build --dir examples/bulletin-board/backend
python3 scripts/local-supabase.py --exec python3 scripts/check-materials-scale.py
```

It starts the real sample (staged path) against a dedicated DB and, with ES256 JWTs from the approved fixture (temporary TLS JWKS relay), sends
the same request sequence for anonymous, the author, a third party and an admin (read, edit, publish toggle, create/delete, grant/revoke rights, read user, list)
in 3 states: fixed data only, after adding 100,000 rows to User, and after also adding 100,000 rows to Post (the list targets Post, so it is
not sent in the last state). For each request, after waiting for the sample's connection to close, it takes the number of rows read from each table from the differences
of `pg_stat_user_tables` and `pg_stat_user_indexes`, and checks that for the 100,000-row tables it is the same as in the empty state
(up to a margin of 2 rows for index point lookups), at most 16 rows in total except for the list, and that the median response time (12 runs) is within twice that of the empty state.
Finally it confirms with its own SELECT that a full scan of 100,000 rows does appear in the same statistics views.
On exit it deletes only the dedicated DB, and prints no credentials.

## Loading connection information for a real Supabase

Put the following 2 variables in `.env` at the project root (ignored by Git).

```dotenv
NYXIS_SUPABASE_URL=https://PROJECT_REF.supabase.co
NYXIS_SUPABASE_ANON_KEY=YOUR_ANON_KEY
```

On every run the script reads `.env` and checks that the 2 variables exist and the URL's format.
Verifying that the connection and Auth configuration are correct is needed separately. Values are never logged.
Values in `.env` take precedence over parent environment variables of the same name, and unspecified values are filled from the parent environment.
Quotes, a leading `export` and comments are supported, but variable expansion, command substitution and
multi-line values are not. Only the 2 variables above are read.

The script is a separate process, so it cannot change the caller's environment.
Run check commands against the real cloud in the following form.

```sh
python3 scripts/local-supabase.py --exec-cloud COMMAND ARG ...
```

This run also rereads `.env` and passes the values to the child process's environment.
Docker and local Supabase do not need to be started. The existing `--exec` still
passes only local connection information and does not use the cloud information in `.env`.
