# Catalog of proofs

A list of the theorems nyxis proves in Lean and of what each of them does not state. The trusted assumptions are in [ASSUMPTIONS.md](../ASSUMPTIONS.md),
and how the connection code supporting the assumptions is built (its responsibilities) is in [docs/connection.md](connection.md).
That no theorem depends on axioms other than the standard three (`propext` / `Classical.choice` / `Quot.sound`) is
checked by `Test/Axioms.lean` during `lake build` (it enumerates every theorem in `Nyxis.*`). Each theorem's Lean statement and its plain-language reading
are in the same file as the corresponding definitions.

## Connection code (the proved part of Assumption 1)

Theorems about pure decoding, restoring and SQL planning state the relation between the input in Lean and a successful return value. Theorems about IO functions
state, assuming normal termination, the return value and the successive IO states. `serve_handler`, `wrap_options` and the like state equations of the processing.
None of them covers the behavior of the outside world beyond the FFI, the actual state of the external DB, TLS, cryptography or the correctness of clock values.
Theorems stating the structure of the returned HTTP response also assume that obtaining the response succeeded. Theorems connecting the real non-health entry through body retrieval, authentication, DB processing and
response construction assume that reading the body completes immediately.
The shared lemmas that decompose normal termination of IO `bind` and `mapM` are in `Nyxis/Internal/IOTrace.lean`.

## Policy toward proving the connection code

The correspondence of the connection code of Assumption 1 as a whole is unproved, and a successful integration test is not regarded as a formal proof. For the parts that have been proved, the theorems and the implementation they cover are listed in the tables above, and those parts are
removed from what is trusted. The connection code as a whole is not declared unprovable merely because it depends on external IO or FFI. For the parts that cannot be proved,
the technical reasons and the remaining assumptions are stated below (the remaining trust is collected into Assumption 1 of `ASSUMPTIONS.md`). If a theorem's statement needs to
change, that decision continues to be left to humans.

## Correspondences still unproved in the connection code

The following is the breakdown of the connection code of Assumption 1 (formerly A4), not a new assumption. Each piece of processing is implemented, but the proofs of the listed correspondences are not.

- **HTTP entry and exit**: decoding raw HTTP, the internals of `Std.Http.Body.Stream.readAll`, the continuation of asynchronous processing returned as a task,
  and consuming and sending the response body are unproved. The current theorems for non-health responses decompose the IO states in the case where the standard `readAll`
  completes immediately, and there is no theorem deriving the execution of the continuation from task completion and scheduling. The health theorems do not need the
  premise of immediate body completion. `ApprovedServer.readAll_response` covers the response inside CORS, and `Cors.wrap_options` shows only the
  equation that the next handler is not called. The Origin permission decision, the structure after header decoration and its correspondence to actual sending remain in Assumption 1.
- **SQL and the real DB**: successful SQL generation and shape checks, the Reader's fetched sequences and return values, and the success order of BEGIN/COMMIT are proved.
  The effect on rows and columns when PostgreSQL executes the generated SQL, isolation, persistence and rollback on failure are unproved.
  The current theorems deal with the return values of the Lean Driver/Reader and have no correspondence to a model representing SQL semantics or the external DB state.
  That the results of point lookups and of SELECTs with a WHERE clause are the current rows in the DB (all of those matching the filter) (`PostgresRun.Chain`) is a premise, and
  that `PostgresMaterials.load` fetches everything for the filters of `Chain`'s premise is by definition, with neither a theorem nor a runtime check
  (a missed fetch only makes the premise false, and in the real DB the RESTRICT / UNIQUE backstop makes the SQL fail).
  The internals of the JSON parser and the lookup semantics of the restored `Map.make` are not unfolded in these connection theorems either.
- **Authentication and construction of the approved sources**: the wiring from the same token, this JWKS document, key preparation, the real clock and success of the approved `Jwt.verify` to the subject
  is proved. The server-generated values are determined by `Generated.fresh` right after authentication, and it is proved up to the point that a request carrying those values is passed to the backend
  (`PostgresHttp.dispatch_success`). The internals of `fresh` (reading the clock, randomness, the UUID's form) are unproved. For curl's
  version check and the internals of the HTTPS fetch, the internals of JWKS/JOSE parsing, key handling, cryptography and claim checks, and clock values, correctness cannot be derived from
  the success equations of those calls alone, and they depend on the approved implementations of Assumptions 1 and 2. For Cedar parsing and embedding and the construction of the PostgreSQL shape too, the correspondence that the values obtained from the source files
  represent the intended syntax and types is unproved (the correspondence with the approved sources of Assumption 3). The projection equations that build the App from the declaration are distinct from the
  proof of authorization safety for that App.
- **External effects and periodic jobs**: the internals of `StorageSign.sign` / `MailSend.send` / `CallSend.call` (starting curl, passing the configuration,
  parsing the response) are unproved. What is proved goes only as far as "`Driver.external` is called only for records (`Authz.External`)"
  (`StagedRun.external`). The outbox of `async` calls has the same boundary: that `Driver.external` calls `Outbox.enqueue` only for records
  is within the scope of `StagedRun.external`, while that the INSERT SQL matches the record's content, that the internal loop
  `Outbox.loop` / `step` sends only the row's content, the avoidance of double sending by `FOR UPDATE SKIP LOCKED` and READ COMMITTED, and
  the retry transitions (`Outbox.settle`) are unproved (confirmed by the integration test `scripts/check-outbox.py`). The outside-world behavior of `Jobs.start` / `loop`, which repeat periodic job runs
  in a separate thread (interval, discarding failed runs), and the outside-world behavior of the internal loop (interval, retries) are unproved;
  what is proved is that each run flows into the same `handleStaged` as HTTP and that both are started in the body of `serve`
  (the equation `ApprovedServer.serve_handler`).
