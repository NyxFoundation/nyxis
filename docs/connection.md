# How the connection code is built — nyxis's responsibilities behind the assumptions

An explanation of what nyxis guarantees by construction in order to support each assumption (Assumptions 1-3) in [ASSUMPTIONS.md](../ASSUMPTIONS.md). What is written here is the implementation's responsibility, not a trusted assumption (where a proved property is mentioned, the theorem name is given). The catalog of proved theorems and of what each of them does not state is [docs/proofs.md](proofs.md). The connection code is trusted for now as Assumption 1, and the parts that have been proved are moved to proofs.md one by one.

## 1. Authentication — determining the principal from the JWT (Assumptions 1 and 2)

Scope: `Nyxis.Internal.SupabaseJwt` / `JwksFetch` / `HttpAuth`.

- The JWKS is fetched over HTTPS on every verification. The JWKS URL is derived in a fixed way from the issuer (core setting `NYXIS_SUPABASE_ISSUER`; `https://host[:port]/auth/v1`); the request's URL, headers and token are never used as the destination. Transport is curl without a shell (8.4 or later; `ApprovedServer.serve` checks the version once at startup and refuses to start if it cannot be confirmed), with `--disable` first, HTTPS only, no redirect following, 3 seconds to connect and 5 seconds for the whole transfer, a body of at most 64KiB, and only HTTP 200 accepted. No sensitive headers are sent, and stderr is discarded. A failed fetch closes to anonymous and never falls back to old keys.
- ES256 JWTs are verified with the approved implementation (OpenSSL's libcrypto and lean-jose / jose-libcrypto / lean-libcrypto). `alg: none` is rejected, and the signature, issuer, audience `authenticated` and expiry are checked with zero leeway. Only a non-empty `sub` without NUL becomes an ID of the entity type in the core settings. Cryptography and JOSE parsing are not hand-written.
- Requests that fail verification and requests without a JWT are treated as anonymous. The Authorization header is accepted only as a single `Bearer` value; duplicates, combined headers, whitespace only, or NUL make the request anonymous. The clock is read per request, after the JWKS fetch.
- The same machine clock is also used for the current time among the server-generated values (4. below).

## 2. HTTP entry and responses (Assumption 1)

Scope: `Nyxis.Http` (shared components on top of `Std.Http`), `Nyxis.Internal.PostgresHttp`, `Nyxis.Internal.HttpResponse`, `Nyxis.Internal.Cors`.

- The request summary passed to a handler is only the method, the path (without the query string), the query string, the few request headers enumerated in `Nyxis.Http.RequestHeader` (Accept, Accept-Language, Content-Type, If-None-Match, If-Match) and the body; Authorization and Cookie are not in that type (`Http.selectHeaders`). The body is limited to 1 MiB; an oversized or non-UTF-8 body is 400 and the handler is not called.
- Responses are built by `Http.responseBuilder`. A handler can set only the few headers enumerated in `Nyxis.Http.ResponseHeader` (Content-Type, Cache-Control, ETag, Location; Set-Cookie is not in the type). Invalid values and Cache-Control's `public` / `s-maxage` are dropped, and for a repeated name only the first value is sent. Without a Content-Type, `text/plain; charset=utf-8`.
- A DB failure (including fetches that do not cover the decision materials, shape mismatches of fetched rows, and SQL or comparison failures) is a fixed 503 with no details, an unreadable body is a fixed 400, and `GET /health` returns a fixed 200 without touching the DB. Only the failure where a 2xx response of an external API call (`sync`) does not match the declared type becomes a fixed 502 with no details after the transaction is rolled back (`PostgresRun.gatewayResponse`). Diagnostic strings of the DB connection, JWKS, curl and JWT appear neither in responses nor in logs.
- CORS (`Nyxis.Internal.Cors`) adds Allow-Origin only for an Origin header (when there is exactly one) that matches the core setting `NYXIS_CORS_ORIGINS` (exact matches of comma-separated HTTP(S) origins; unset or empty means none allowed, and an invalid setting refuses startup), additionally adds fixed Allow-Methods / Allow-Headers to preflight (OPTIONS) responses, and adds `Vary: Origin` to every response. OPTIONS returns an empty 204 before reading the body, authentication, the handler and the DB. Cookie credentials are not allowed.
- The real startup `Nyxis.Internal.ApprovedServer.serve` starts only an App built from the declaration (7. below).

## 3. Staged execution — 1 request = 1 SERIALIZABLE transaction on 1 new connection (Assumptions 1 and 2)

Scope: `Nyxis.Internal.PostgresRun.handleStaged` / `runStaged` (the path used by the real startup `PostgresHttp.handleVerified` → `ApprovedServer.serve`), `PostgresMaterials`, `PostgresSql`, `PostgresResult`, `PostgresWrite`, `PostgresShape`.

- For each action call of the handler, only the entities needed for the decision are fetched by primary-key point lookups (`PostgresMaterials.load`). Where the decision looks at rows through a filter — the target table of a list, rows with the same values as a uniqueness tuple, rows referencing rows deleted by a deletion (per cascade stage), and membership rows (`loadMemberships`) — they are fetched by a SELECT with the filter as its WHERE clause (`PostgresSql.selectFiltered`). The only SQL is core-generated SELECTs, and filter constants are passed as parameters too.
- After confirming with an executable check that the fetch covers the decision materials (`Authz.coversStep`: presence of the target row, entities reachable from the request at the policy's level, presence of referenced rows, and the decision materials of each cascaded row and the state after it), the decision is made from the fetched rows only (`Authz.step`). Fetched rows are checked for column types and required attributes against the shape built from the approved source (`PostgresShape`), and proposed values are checked before issuing as well.
- Only the issued operations are turned into SQL (`PostgresSql`; identifiers from the schema, values as parameters), and the result of each operation is compared with the expectation of the preceding `Store.apply` (`PostgresRun` / `PostgresResult` / `PostgresWrite`; writes need commandOk, zero rows and columns, an affected count of 0 or 1, and the per-operation tag). Anything that fails a check, mismatches the shape, disagrees or fails is rolled back and no response is returned. A response is returned only after a checked COMMIT.
- What is trusted here is that "a point lookup's result is the current row in the DB, and the result of a SELECT with a WHERE clause is all of the current rows in the DB that match the filter (the SQL comparison agrees with the model's `Db.Filter.matches`)" (`PostgresRun.Chain`; the set of filters is `Authz.rowFilters`). This is the trust of Assumption 1, not a new assumption.
- The approved source's constraints are also placed in the DB by the same rules (`UNIQUE (column, …)` in `PostgresSql.createTable`; generated columns `_nyxis_ref_<column>` holding the stored-form ID of reference columns with `FOREIGN KEY … ON DELETE RESTRICT` from `PostgresSql.foreignKeys`; indexes on the referencing side. `PostgresInit.provision` adds them after all tables). The model judges first, and a cascading delete explicitly issues the DELETE of each row the model judged, deepest rows first (the DB's CASCADE is not used). The DB constraints are a backstop: if the decision is wrong (if the fetch disagrees with the DB), the SQL fails and the whole request closes (rollback, 503). Whether the constraints exist does not change the decision's conclusion, so this backstop needs no new trust.
- The reference path (`PostgresRun.handle`), which reads the current rows of all tables to rebuild the `Store` (`PostgresLoad`), computes the model `Runtime.handleRequest` purely and likewise turns the issued operations into SQL and compares them, is not used by the real startup. A core check (`scripts/check-postgres-values.py`) confirms both paths, each against a separate real DB, against the same expectations (responses, remaining rows). Trusting on this path that the `Store` is the current rows of the DB is the same kind of trust as above, not a new item. The shape check (`PostgresShape`) covers the fetched rows on the staged path and all rows before authorization on the reference path; both check proposed values before issuing.
- Tables are built by an explicit executable separate from HTTP (`PostgresInit.provision`; checks the plan of all CREATE TABLEs before connecting and runs it SERIALIZABLE on a new connection), which fails if a table already exists. It performs no migrations, seed data or permission creation.
- The PostgreSQL client is lean-pq (a pinned version) with the human-approved `scripts/patches/lean-pq-ownership.patch` applied (ownership and resource-release fixes only; no added bindings). It is used only inside nyxis; handlers are not given the connection, raw SQL or the client's operation API. A connection is not reused after an error.

## 4. Server-generated values (Assumptions 1 and 2)

Scope: `Nyxis.Internal.Generated.fresh` → `PostgresHttp.dispatch`.

- The unique ID is created exactly once, right after authentication, as a version 4 UUID from 16 bytes of the runtime's randomness (`IO.getRandomBytes`; the OS randomness source), and together with the current time it is passed as `Runtime.AuthenticatedRequest.generated` to the handler (for proposing values) and to the authorization layer (the context of actions whose `context` declares `now` / `id` in the approved source). It is not derived from any part of the request, and the handler cannot replace it (main theorem).
- The ID's uniqueness depends on the runtime's randomness source, and no theorem claims it (even on a collision, the insert closes to 409). There is one set of generated values per request (a handler inserting several rows can use the same ID as the primary key of only one row, and the decision of every row in a list sees the same `now`).
- Using the generated values for insert primary keys and proposed values is up to the handler; nyxis does not enforce it. That a proposed value equals a generated value is judged by the policy writing `context.values.x == context.now` / `== context.id`; primary keys cannot be referenced from Cedar expressions, so using the generated ID as the primary key is the responsibility of the handler's construction (and of the second sample's integration test).

## 5. Declared external effects — Storage, mail, external API calls (Assumptions 1-3)

Scope: `Nyxis.Internal.StorageSign` / `MailSend` / `CallSend` / `ExternalSend` / `Outbox`, `PostgresRun.runStaged`.

- If the decision recorded an external effect (`Authz.External`: principal, generated values, action, target and content, as determined by `Authz.payloadOf` for the permitted row), then for that record only, nyxis asks Storage to issue, sends mail, calls the external API, or writes an `async` call to the outbox (`PostgresRun.sendExternal` → `Driver.external` → `ExternalSend.send` → `StorageSign.sign` / `MailSend.send` / `CallSend.call`; an `async` call goes to `Outbox.enqueue`). That the value of the result (`Authz.ExternalResult`: a signed URL, the response of a `sync` call, or no result) does not change the decision is `Authz.step_external_indep`. Execution continues with the result obtained. The handler cannot propose the recipient, the content or the destination (the effect's type has no such arguments; only the proposed values of an action that takes `context.values` with `call` enter the body, after passing the decision).
- A failure to issue or send (connection, TLS, 5xx, SMTP rejection; for a `sync` call, a transport failure or a failure to decode the response) is an exception; it rolls back together with the DB operations of the same transaction and returns 503 (it is never silently treated as success). Only the failure where the 2xx response of a `sync` call does not match the declared type (`CallSend.invalidResponse`: not JSON, a declared key missing, a type mismatch) is mapped by `PostgresRun.handleStaged` to a fixed 502 after the rollback (`PostgresRun.gatewayResponse`) (the other branch of `PostgresRun.handleStaged_success`: the response is a fixed value, and the transaction of the same body `PostgresRun.stagedBody` failed with that exception). If COMMIT fails after a successful issuance or send, the DB is rolled back but the issuance or send cannot be undone (an effect outside the DB; for a `sync` call this is the idempotency-key assumption of Assumption 3). Even then, a response is returned only after a checked COMMIT, so the URL or response does not reach the user; a URL that does reach the user always targets an object of a permitted row, and mail and calls that are sent always contain only the declared columns of a permitted row (and proposed values that passed the decision) (in an app that records "sent" in the DB, only that update may be rolled back and resent).
- Storage: the issuance URL (`{NYXIS_STORAGE_URL}/storage/v1/object/[upload/]sign/{bucket}/{path}`) is built in a fixed form from the core settings and the record (the request's URL, headers and body and the handler's values are not used). The path is `table/<primary key>/<name>`, whose segments are limited to alphanumerics, `-` and `_`; nothing is issued for other primary keys or names (`Db.objectPath`). Transport is the same approved curl as for the JWKS (HTTPS only, no redirect following, 3 seconds to connect and 5 seconds for the whole transfer, a body of at most 64KiB), and the credential (`NYXIS_STORAGE_SERVICE_KEY`) is passed in the configuration on standard input, never in arguments. The expiry of a download URL is the core constant `StorageSign.expiresIn` (600 seconds) and cannot be changed by the request (Storage decides the expiry of an upload URL). If Storage answers "no such object" (404, or 400 with `not_found`), the result is `Outcome.notFound`.
- Mail: the relay (`NYXIS_SMTP_URL`) and sender (`NYXIS_MAIL_FROM`) are fixed by the core settings. Recipient and sender are limited to a single address of printable ASCII (whitespace, `<>`, `"`, `\`, `,` and `;` are rejected), newlines and control characters are removed from the subject header (non-ASCII becomes an encoded-word), and the body is sent as UTF-8 text/plain. The message is written to a temporary file readable only by the owner, passed with curl's `upload-file`, and deleted after sending (curl's SMTP cannot take both the configuration and the body on standard input at once). `--disable` first, `--proto =smtp,smtps`, no redirect following, 5 seconds to connect and 20 seconds for the whole transfer. Credentials are passed in the configuration on standard input, never in arguments.
- External API calls (`sync`): the URL is the base URL of the approved source's `@external` destination plus a fixed path (`{key}` is the primary key), or the value of the row's URL column (`https://` only; `Db.callUrl`); the request's URL and headers and the handler's values are not used. The authentication header is built at startup per destination from the core setting `NYXIS_EXT_<name>` (the approved source holds only the environment variable name) (`CallSend.Config.load`; startup is refused if it is missing), passed in the configuration on standard input, and never appears in arguments, records, responses or exceptions. The body is JSON of the row's declared columns and the proposed values that passed the decision (none for `GET` / `DELETE`). The connection and whole-transfer limits and the response body limit are core settings (`NYXIS_CALL_CONNECT_TIMEOUT` / `NYXIS_CALL_MAX_TIME` / `NYXIS_CALL_MAX_RESPONSE_BYTES`; defaults 3 seconds, 10 seconds, 64KiB; a `<seconds>s` in the approved source can only shorten the whole-transfer limit). A 2xx response is read as JSON and decoded leniently into the record type declared in the approved source (`CallSend.decode`: only a missing declared key or a type mismatch is rejected; extra keys are dropped). A non-2xx response passes the status code and raw body to the handler as `Outcome.calledError` (the transaction continues). A decoding failure is the fixed 502 above. The integration check against a mock API is `scripts/check-external-calls.py` (`Test/ExternalCalls.lean`: no send on deny, the authentication header, dropping extra keys, 502 and rollback for missing keys and type mismatches, non-2xx, transport failures, keys never shown).
- External API calls (`async`; the outbox): `external` of `PostgresRun.driver` writes one row for the permitted record to the reservation table `_nyxis_outbox` on the request's own connection (the same SERIALIZABLE transaction) (`Outbox.enqueue`; primary key `<request's unique ID>-<number>`, principal, action, target, destination name, method, resolved URL, body JSON, `pending`; keys are not written). Nothing is sent, and the handler receives `ok none`. If the request's COMMIT fails, this row does not remain either. The table's DDL, `PostgresSql.outbox`, is emitted by `PostgresInit.plan` after the approved source's tables (its form is fixed in docs/external-calls.md §4.3; it is invisible from the approved source's tables). After COMMIT, nyxis's own internal loop (`Outbox.loop`; `ApprovedServer.serve` starts it in a separate thread only when the approved source declares `async`; it makes no decisions), at the interval of the core setting (`NYXIS_OUTBOX_INTERVAL_SECONDS`, default 5 seconds), takes due `pending` rows one at a time with `FOR UPDATE SKIP LOCKED` in a READ COMMITTED transaction (so two instances never send the same row), sends only that row's content with the same transport policy as `sync` (approved curl, HTTPS only, the authentication header per destination from the core settings; `CallSend.arguments` / `configTextJson`), and updates its state in the same transaction (`Outbox.step` / `settle`): 2xx → `sent`, 4xx → `failed`, other status codes and transport failures → increment `attempts` and retry after `NYXIS_OUTBOX_BACKOFF_BASE_SECONDS × 2^attempts` seconds, `failed` at `NYXIS_OUTBOX_MAX_ATTEMPTS` (default 8). The response body is discarded, and `failed` rows are not deleted. A row whose state update or COMMIT failed after sending (the process crashed) is sent again (at-least-once delivery; part of "what the theorems do not state" in Assumption 2). If there is an `async` declaration but no destination setting (`NYXIS_EXT_<name>`), startup is refused (`Outbox.check`). The integration check is `scripts/check-outbox.py` (`Test/Outbox.lean`: no record on deny, no send during the request, 2 rows for 1 request, no remaining row when COMMIT fails, each row exactly once with internal loops in 2 processes, resend on 5xx → 2xx, immediate `failed` on 4xx, `failed` at the maximum attempts, keys never shown).
- Diagnostics appear neither in responses nor in logs.

## 6. Periodic jobs and the service principal (Assumption 3)

Scope: `Nyxis.Internal.Jobs`, `ApprovedServer`.

- The service principal is the entity `Service::"<configured ID>"` of the reserved type `Service` (not a table, with no rows or attributes; `CedarSchema` rejects attributes, parents, tags, membership rows, attachments and being an effect target), used only for periodic job runs (`Authz.Principal.service`).
- From the core settings `NYXIS_SERVICE_PRINCIPAL` (the service principal's ID) and `NYXIS_JOB_INTERVAL_SECONDS` (the interval; the core accepts only 1-86400 seconds and has no default; the second sample's `Main` passes 60 when unset), each periodic job the app declares in `App.jobs` is run in a separate thread of the same process at a fixed interval, as a request with principal `Service::"<ID>"`, fresh server-generated values and `job := some i`, through `PostgresRun.handleStaged` (the same staged path as HTTP, 1 run = 1 transaction). A failed run is discarded and run again at the next interval. Jobs are written in the same type as handlers (no IO).
- The HTTP entry (`PostgresHttp.dispatch`) only builds requests with `job := none`, and builds the principal only from the JWT verification result and the deployment's user type (`HttpAuth.principalOf`). The deployment carries a proof that the user type is neither `Anonymous` nor `Service` (`Deployment.user_not_service`), so even if a JWT's `sub` equals the configured ID, that principal is `User::"<sub>"` and never the service principal.
- Startup is refused if the setting is present while the approved source does not declare `entity Service;`, or if periodic jobs are declared while the setting is absent.

## 7. Construction of the approved sources (Assumption 3)

Scope: `Nyxis.Build`, `Nyxis.CedarSchema`, `Nyxis.CedarPolicy`, `Nyxis.Approved`, `Nyxis.Internal.ApprovedServer`.

- The authorization inputs are built at build time from the application-side declaration `nyxis_approved name from "<schema>" and "<policies>"`. `Nyxis.CedarSchema` reads the `.cedarschema` and checks the effect declarations (`@effect` and the parent, membership row, uniqueness, referential integrity and attachment annotations), and `Nyxis.CedarPolicy` builds the `.cedar` into the same abstract syntax as Cedar 4.13's parser. If construction fails, `lake build` fails. Lake's `input_file` / `needs` make changes to the approved sources trigger a rebuild.
- `name.app` accepts only the router (and the periodic jobs); the real startup `Nyxis.Internal.ApprovedServer.serve` accepts a `Deployment` holding the declaration, the shape and the user type, plus the router (and also the port, connection string, issuer, CORS settings, external effect settings and service principal settings), and always builds the App internally from the declaration.
- The construction code is not a proof target; its behavior is confirmed by `Test/Schema.lean`, `Test/Policy.lean` and the sample's `BulletinBoardTest/Model.lean` (agreement between values built from the approved source and hand-written abstract syntax). Validation of the policies by Cedar itself (consistency with the schema) is done by `cedar validate`.

## 8. Auditing the application (Assumption 3)

Scope: `Nyxis.Handler`, `Nyxis.AppCheck` (the command `nyxis_check_app`).

- `Nyxis.Handler` has no constructor that lifts IO or accepts DB operations or state.
- `nyxis_check_app` examines every constant other than those of the trusted modules fixed when the checker was compiled (nyxis and its dependencies such as Lean, Std and Cedar), and rejects references to `dbgTrace*` / `panic*` / `ptrAddrUnsafe` / `unsafeCast` / `sorryAx` / `setImplementedBy`, unsafe declarations, extern and implemented_by attributes, initializers, macro and elaborator attributes, and dependence on axioms other than the standard three (`propext` / `Classical.choice` / `Quot.sound`) (including an `axiom` declared by the app and `native_decide`, since a proof of a false bound would allow reads and writes without bounds checks). Private helper functions and wrappers in other modules are covered too.
- Imports from the app of lean-pq, JOSE and the `Nyxis.Internal.*` modules that use them are rejected by the audit through the dependencies' extern attributes (`Nyxis.Internal.PostgresShapeBuild` is rejected through its elaborator attribute). Imports of internal modules without constants the checks catch, such as `Nyxis.Internal.Generated` / `HttpAuth` / `CallSend`, are not caught by the audit, but their processing is IO and cannot be called from the `Handler` type.
- Limits: the audit inspects the environment after elaboration and imports; it is not a build sandbox. It cannot prevent IO during the build before the check is reached, commands that leave no constants, code added after the check, or builds that delete or replace the check, and it does not restrict the contents of `main`'s IO. The completeness of the deny list is unproved. These are trusted as Assumption 3.

## 9. Properties by types and definitions (not assumptions; mostly from the structure of types and definitions rather than theorem statements)

- A handler cannot specify or replace the principal, the resource or the effect (the `Handler` type and the structure of `Authz.step`; that the principal and generated values cannot be forged is stated as a theorem by the main theorem's `i.principal = r.principal ∧ i.generated = r.generated`). nyxis determines the principal from that request's JWT, the resource from the current DB row, and the effect from the schema's declaration.
- Issued DB operations stay within the declared effect (kind, table, and for updates, columns) (`Db.Operation.withinEffect`).
- The Cedar evaluator called by the authorization layer `Authz.step` is the cedar-spec Lean model itself (`Cedar.Spec.isAuthorized`), and no other implementation is used. Hence no assumption that "the Cedar implementation agrees with the model" is made (the runtime that executes the evaluator is Assumption 1).
- The entities of the decision are the current rows that conform to the schema and the schema's actions, and among the values of parent-pointing columns (`@parents`) and membership rows (`@memberships`), those of the declared parent types become ancestors (`Materials.rowAncestors_ty`). The authorization layer's actual decision (`Authz.permits`) uses only the entities reachable from the request within a finite number of levels (`Authz.materials`, cedar-lean's `sliceAtLevel`). That it agrees with the decision over everything is a theorem (`Authz.permits_authorized`; proofs.md).
- The request headers a handler can read and the response headers it can set are limited to enumerations (2. above). "No name outside the enumeration appears" is a property of types and definitions, not a theorem statement.
- Promises about the decision materials: the principal's entity is always the current row in the DB (no entity if absent). The resource is the current row in the DB, or, for an insert where the row does not exist, the proposed row (except the principal itself). The proposed values of inserts and updates are `context.values`. A write's `Outcome.ok` returns no row. Even when a permitted operation ends in `conflict` / `notFound`, the operation is recorded (the state does not change).
